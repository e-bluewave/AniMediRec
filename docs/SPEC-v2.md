## 0. 全体方針

8項目は独立していません。**バックエンド（サーバー）が必要なもの**と、**今のまま（ブラウザだけ）で実現できるもの**に分かれます。

| 項目 | 内容 | バックエンド | 難易度 |
|---|---|---|---|
| ① | 施設ごとのログイン | 必要（本格実装の場合） | 中〜高 |
| ② | 個体管理番号 | 不要 | 低 |
| ③ | 自動保存・自動復元 | 不要（localStorage/IndexedDB） | 低〜中 |
| ④ | クラウド同期 | 必要 | 高 |
| ⑤ | 永続保存 | ③④に内包＋運用設計 | 中 |
| ⑥ | 日付順ソート | 不要 | 低 |
| ⑦ | 体重の単位 kg/g | 不要 | 低 |
| ⑧ | CSV/JSON/PDF出力 | 不要 | 中 |

**①④⑤は実質ひとつの課題**（＝クラウド基盤の導入）です。ここだけ切り離して考えるのが効率的です。

### 推奨する実装順序

**Phase 1（バックエンド不要・すぐ効く）**
⑥ソート修正 → ②管理番号 → ⑦単位kg/g → ③自動保存 → ⑧CSV/JSON出力

**Phase 2（クラウド基盤の導入）**
①ログイン ＋ ④同期 ＋ ⑤永続保存（論理削除・バックアップ・監査ログ）

**Phase 3**
⑧PDFカルテ、権限の細分化、投薬リマインダー等

## ⓪ 先に共有すべき既存の不具合

仕様検討の前提として、現行コードに以下の問題があります。改善と同時に直すことを推奨します。

1. **個体登録フォームの大半が保存されていない**
   `savePetInfo()` が保存しているのは 名前 / 種類 / 体重 / 写真 / 種別アイコン のみ。
   生年月日・来た日・部屋エリア・性別・体格・性格・既往歴・かかりつけ病院（病院名/電話/メモ）は
   入力欄はあるが保存もされず、編集時に再表示もされません。

2. **「⚠️要観察」バッジが消えない**
   `pet.logs.find(...)` で過去全期間を見ているため、一度でも△✕が付くと永久に点灯します。
   「直近7日以内に△✕がある場合」など期間条件が必要です。

3. **HTMLエスケープが無い**
   名前やメモを `innerHTML` にそのまま埋め込んでいます。`<` や `"` や `'` を含む入力で表示が崩れます
   （例: メモに `"` を含むと `onclick` 属性が壊れて編集ボタンが効かなくなる）。
   併せて `onclick="openImageModal('${log.photo}')"` は写真のbase64文字列を丸ごとHTML属性に
   埋め込んでおり、動作も重くなります。`data-id` 経由での参照に変更すべきです。

4. **記録の時刻が「保存した瞬間の時刻」固定**
   過去日付を選んで記録すると、日付は過去・時刻は現在という組み合わせになります（⑥と関連）。

5. **「自由備考」だけタグ定義が無い**（`categoryTagMap` に未登録）ため、状態判定のみの入力になります。意図通りか要確認。

## ① 施設ごとのログイン機能

### 現状
アクセス制限なし。URLを知っていれば誰でも全データを閲覧・編集・削除できる。

### 方式の選択肢

| 方式 | 内容 | 安全性 | 備考 |
|---|---|---|---|
| A. 簡易パスコード | 施設コード＋暗証番号をJS内で照合 | ✕ 気休め | ソースを見れば突破可能。**動物の医療情報を扱うなら非推奨** |
| B. サーバー認証 | Firebase Auth / Supabase Auth 等 | ◎ | ④と同時導入が前提 |
| C. Basic認証 | サーバー側の設定で丸ごと保護 | △ | 施設単位の分離や職員別の記録者名は不可 |

**推奨: B**。④クラウド同期をやるなら必然的にBになります。「まずは社内だけで試す」段階ならCが最も早くて安全（サーバー設定のみ）。

### 設計案（B の場合）

- **ログイン画面**: 施設コード ＋ メールアドレス（またはスタッフID）＋ パスワード
- **データ構造**: 施設(facility) > 職員(user) > 個体(animal) > 記録(log)
- **権限ロール**
  - `admin` 管理者: 個体の削除、職員の追加、エクスポート、全操作
  - `staff` 一般職員: 記録の追加・編集、個体の登録
  - `viewer` 閲覧のみ: 読み取り専用（ボランティア・実習生・獣医への共有用）
- **セッション**: ログイン状態を保持（自動ログイン）／一定時間無操作で自動ログアウト／明示的ログアウトボタン
- **記録者の記録**: 各記録に「誰が入力したか」を自動付与 → ⑤の監査ログにつながる
- **パスワード**: 必ずサーバー側でハッシュ化して保存。クライアントに平文を置かない。

### 検討が必要な点
- 施設をまたいで見られる本部アカウントは必要か
- 職員のアカウント発行は管理者が行うか、招待リンク方式か
- 共用タブレットでの運用（誰でも触れる端末）では、PINコードによる簡易切替も併用したい

## ② 個体管理番号

### 現状
同名の個体を区別できない。一覧でも詳細でも名前のみが手がかり。

### 設計案

- **個体に `code`（管理番号）を追加。施設内で一意。**
- **採番方式はハイブリッド**
  - 手入力可（既存の紙台帳・ケージ番号をそのまま引き継げる）
  - 空欄なら自動採番
- **自動採番の書式案**（設定で選択できると理想）
  - 連番方式: `0001`, `0002`, ...
  - 年度＋連番: `2026-0012`（保護施設向き。受入年が分かる）
  - カテゴリ略号入り: `DC-0012`（犬猫）, `RP-0007`（爬虫類）
- **重複チェック**: 保存時に施設内の既存番号と照合し、重複なら警告して保存させない
- **表示箇所**: 一覧カード、詳細ヘッダー、検索対象、CSV/PDF出力
- **既存データの移行**: 番号未設定の個体には `UNREG-0001` 形式を自動付与

### 併せて追加を検討したい識別情報
- マイクロチップ番号
- 犬の鑑札番号・狂犬病予防注射済票番号
- 個体識別用の特徴メモ（毛色・柄・欠損など）

## ③ データの保存機能（自動保存・自動復元）

### 現状
`pets` 配列がメモリ上にあるだけ。リロード・タブを閉じる・スマホのタブ破棄で全消失。

### 設計案（第一段階: 端末内保存）

- **保存先**: `localStorage`（構造データ）＋ `IndexedDB`（写真）
- **キー**: `animedirec:v1:pets` / `animedirec:v1:meta`
- **保存タイミング**: データを変更する全操作の直後に `saveState()` を呼ぶ
  （個体の登録/編集/削除、記録の追加/編集/削除、体重の追加/編集/削除）
  → 各関数に散らさず、**変更関数の出口を1本化**して呼び出すのが安全
- **復元**: 起動時に `loadState()`。データが無ければ空の状態（またはデモデータ）で開始
- **スキーマバージョン**: `schemaVersion: 1` を保存。将来の項目追加時に自動マイグレーション

### 最大の注意点: 写真の容量

現在、写真は base64 の data URI として `pets` に直接埋め込まれています。
**localStorage の上限は概ね 5MB**。スマホ写真は1枚 2〜5MB あるため、**写真を2〜3枚登録した時点で保存が失敗します**（`QuotaExceededError`）。

対策（併用推奨）:

1. **保存前に必ず圧縮** — canvas で長辺 1280px 程度に縮小し JPEG 品質 0.7 で再エンコード
   → 1枚あたり 100〜200KB 程度に収まる（排泄物・患部の記録用途には十分な画質）
2. **写真本体は IndexedDB に Blob で保存**し、`pets` 側には画像IDのみ持つ
   → 容量上限が数百MB〜になり、文字列化のオーバーヘッドも無くなる
3. クラウド導入後は Storage にアップロードしてURL参照に切替

さらに、**保存に失敗した場合はユーザーに明示的に通知**する（黙って消えるのが最悪）。

## ④ クラウドの同期

### 要件
- スマホ・PC・タブレットのどれからでも同じデータを見たい
- 複数の職員が同時に記録しても壊れない
- 施設内でWi-Fiが弱い場所（ケージ棟など）でも記録でき、後から同期されてほしい

### 基盤の選択肢

| 候補 | 長所 | 短所 |
|---|---|---|
| **Firebase**（Firestore + Auth + Storage） | オフライン対応とリアルタイム同期が標準装備。静的HTMLのままCDN読み込みで導入可。認証も込み | 料金体系が読みにくい／ベンダーロックイン |
| **Supabase**（Postgres + Auth + Storage） | SQLで扱え、エクスポートが容易。自前ホストも可能 | オフライン同期は自前実装が必要 |
| 自前サーバー（PHP/Node + MySQL） | 完全に自由・データを自社管理 | 開発／運用／バックアップ／SSLすべて自前 |

**推奨: Firebase**。今回の用途（オフライン耐性・多端末・リアルタイム・少人数）に最も素直に噛み合います。

### データ構造案（Firestore）

```
facilities/{facilityId}
  ├ users/{uid}          { name, role, createdAt }
  └ animals/{animalId}   { code, name, category, type, breed, sex,
                           birth, birthAccuracy, arrivedAt, area, build,
                           personality, history, hospital{name,tel,memo},
                           weightUnit, photoPath,
                           createdAt, updatedAt, updatedBy, deletedAt }
      ├ logs/{logId}     { recordedAt, date, timezone, time, category,
                           statusFlag, tags[], memo, photoPath,
                           recordedBy, updatedAt, deletedAt }
      └ weights/{id}     { date, grams, updatedAt, deletedAt }
```

### 同期の考え方
- **記録は追記型**なので競合はほぼ起きない（同じ記録を2人が同時に編集する場面が稀）
- 競合時は `updatedAt` が新しい方を採用（Last-Write-Wins）で十分
- **削除は物理削除せず `deletedAt` を立てる**（⑤へ）
- オフライン: Firestore の永続化を有効にすれば、圏外で記録 → 復帰時に自動送信
- セキュリティルール: 自分が所属する `facilityId` 配下しか読み書きできないよう制限

### 移行
③で localStorage に貯めたデータを、初回ログイン時にクラウドへ一括アップロードする移行処理を用意します。

### コスト感
数十頭・年間数千記録・写真圧縮済みの規模であれば、無料枠〜月数百円程度に収まる見込みです。

## ⑤ 永続保存機能

③（端末内で消えない）④（端末間で共有）と重なるため、⑤は **「消えない・戻せる・追える」** の運用設計として整理します。

### 1. 論理削除（ゴミ箱）
現在は個体削除も記録削除も**即時・完全消去**で、取り返しがつきません。
- 削除操作は `deletedAt` を立てるだけにする
- 「ゴミ箱」画面から30日以内なら復元可能
- 30日経過後に自動で物理削除（または管理者のみ完全削除可）

### 2. 監査ログ
施設で複数人が扱う以上、「誰がいつ何を変えたか」は必須です。
- 各レコードに `createdBy` / `updatedBy` / `updatedAt`
- 重要操作（個体削除・記録の改変）は操作履歴として別途保存

### 3. 自動バックアップ
- 日次で全データのJSONスナップショットを保存し、直近30世代を保持
- 管理者はいつでも過去のスナップショットをダウンロード可能（⑧と連動）

### 4. 保存期間ポリシー
施設の方針に合わせて「記録は最低○年保持」を決めておく（譲渡・監査・訴訟対応のため）。

## ⑥ 日付順のソート

### 原因
記録の追加は `pet.logs.unshift()`（配列の先頭に差し込む）で行われ、**表示時にソートしていません**。
そのため過去日付を後から登録すると並びが崩れます。体重履歴も `push()` 順のままグラフを描くため、
過去日を後から追加すると折れ線が左右に往復します。

### 設計案

1. **保存順に依存せず、表示の直前に必ずソートする**
2. ソートキーは `日付 → 時間帯（朝<昼<夜）→ 時刻`
3. より確実なのは **`recordedAt`（ISO8601の日時）をデータに持たせて一元管理**すること
   - 例: `"2026-09-04T08:15:00+09:00"`
   - 表示用の `date` / `time` はここから導出
   - 既存データは移行時に `date + time` から生成
4. 既定は**降順（新しい順）**。検索結果の一覧も同じ規則。昇順／降順の切替ボタンがあると便利
5. **体重履歴も日付昇順でソートしてからグラフ描画**する
6. **記録の時刻を手入力できるようにする**（⓪-4の問題）
   - 過去日を選んだ場合は、時刻欄を初期値「未入力」にして手入力を促す
   - 時間帯（朝/昼/夜）から既定時刻（08:00/13:00/20:00）を補完する案も可

## ⑦ 体重グラフの単位（kg / g）

### 現状
`weight` が `"3.2kg"` という**文字列**で保持され、単位はkg固定。
0.06kg（60g）のヒョウモントカゲモドキのような小動物では、グラフの目盛りも読みにくくなります。

### 設計案

1. **個体ごとに `weightUnit: 'kg' | 'g'` を持たせる**
   - カテゴリから初期値を自動提案（犬・猫→kg、爬虫類/げっ歯類/鳥類→g）
   - 個体登録・編集画面で変更可能
2. **内部保存は g（グラム）の整数に統一する**
   - 単位混在による事故と、小数計算の誤差を根本的に防げる
   - `weight: "3.2kg"`（文字列）→ `grams: 3200`（数値）へ移行
   - 既存データは移行時に kg 値 × 1000 で変換
3. **表示は `formatWeight(grams, unit)` で一元化**
   - kg → `3.2 kg`（小数第2位まで）
   - g → `60 g`（整数）
4. **入力欄**: 単位をラベル表示し、`step` と桁数を単位に応じて切替（kgは0.01刻み、gは1刻み）
5. **グラフ**: Y軸ラベル・データラベル・目盛り幅を選択単位に合わせる
6. 将来 lb（ポンド）等を足す場合も同じ仕組みで拡張可能

### 併せて検討したい
- 前回比の表示（`+0.1kg (+3.2%)`）
- 急激な増減（例: 1週間で10%以上減）を自動で警告表示 ← 健康管理アプリとして価値が高い
- 目標体重・適正体重レンジの設定とグラフへの帯表示

## ⑧ データエクスポート機能

### 8-1. CSV出力

**出力種別**
- 記録CSV: `管理番号, 名前, カテゴリ, 日付, 時間帯, 時刻, 記録種別, 判定, タグ, 備考, 記録者`
- 体重CSV: `管理番号, 名前, 日付, 体重, 単位`
- 個体一覧CSV: 個体の全属性

**オプション**: 期間指定（開始日〜終了日）／対象（この個体のみ／カテゴリ単位／施設全体）

**技術的な注意（Excelで開く前提なら必須）**
- 文字コードは **UTF-8 + BOM**（BOMが無いとExcelで日本語が文字化けします）
- 改行は CRLF
- カンマ・改行・ダブルクォートを含むフィールドは `"` で囲み、内部の `"` は `""` にエスケープ
- 管理番号が `0001` のような形式の場合、Excelが数値と解釈して先頭0を落とすため、`="0001"` 形式での出力オプションを用意

### 8-2. JSONバックアップ

- 全データを1ファイルで書き出し（`schemaVersion` を必ず含める）
- **インポート（復元）機能とセットで実装**（出せるだけでは「バックアップ」になりません）
- 写真を含めるかどうかを選択可能に（含めるとファイルが数十〜数百MBになり得る）
- インポート時は **「全置換」か「マージ（管理番号で突合）」** を選ばせ、実行前に件数を提示して確認

### 8-3. PDFカルテ

**想定用途**: 通院時に獣医へ渡す／譲渡時の引き継ぎ／施設監査

**構成案**
1. 表紙: 写真・管理番号・名前・カテゴリ・種類・性別・生年月日・かかりつけ病院・既往歴
2. 体重推移グラフ（期間指定）
3. 期間内の記録一覧（判定を色分け、時系列順）
4. 写真付き記録のサムネイル一覧
5. 「通院用サマリー」モード: 直近2週間の △✕ 記録のみを1枚に凝縮 ← 実用性が高い

**実装方式**
- **推奨: 印刷用CSS（`@media print`）＋ ブラウザの印刷→PDF保存**
  日本語フォントの問題が起きず、追加ライブラリ不要で軽い
- ライブラリ方式（jsPDF + html2canvas）は、日本語フォントの埋め込みが必要でファイルが重くなる。
  サーバー生成なら Puppeteer が確実だが、バックエンド前提

## 追記 (2026-09-11): 方針確定と無料運用ルール

### 決定事項

> **①④⑤ → (a) サーバー（クラウド）を本格導入する。ただし費用は一切かけない。**

卒業制作のため、**課金プランへの切り替え（クレジットカード登録）を一切行わない**前提で設計します。
下記は Firebase の無料枠 (Spark プラン) のみで完結させるための具体ルールです。Spark プランはクレジットカード登録が不要で、無料枠を超えると機能が一時停止するだけで、勝手に課金されることはありません。

### 無料枠の内訳と本アプリでの想定消費

| サービス | 無料枠（目安） | 本アプリでの用途 | 想定消費 |
|---|---|---|---|
| Firestore（DB） | 保存 1GB／読み取り 5万回・日／書き込み 2万回・日／削除 2万回・日 | 個体・記録・体重・ユーザー情報 | 数十頭・数千記録でも保存量は数MB程度。読み取り回数が唯一の注意点（下記） |
| Authentication | 無制限・完全無料 | 施設ログイン（メール／パスワード） | 制限なし |
| Cloud Storage | 保存 5GB／ダウンロード 1GB・日／アップロード 20K回・日 | 写真（排泄物・患部・個体写真） | 圧縮後 1枚150KB前後 → 5GBで3万枚以上保存可能 |
| Hosting | 保存 10GB／転送 360MB・日 | アプリ本体の配信 | 静的ファイルのみなので誤差レベル |

**Cloud Functions は使いません。** Functions の無料枠 (Sparkプラン) は限定的で、多くの用途で結局 Blaze プラン（従量課金・カード登録必須）への切り替えを求められます。本アプリはクライアント側の処理とFirestoreセキュリティルールだけで完結する設計とし、サーバーサイド関数を必要としません。

### 無料枠を守るための設計ルール（実装で守ること）

1. **写真は必ずアップロード前に圧縮する**（長辺1280px・JPEG品質0.7）。生の写真をそのまま上げると Storage 5GB をすぐ消費します。
2. **一覧画面で全記録を無条件に読み込まない。** 個体一覧は個体ドキュメントのみ取得し、記録（logs）はその個体の詳細画面を開いたときだけ購読する。検索も「開いている施設の全記録」を毎回舐めるのではなく、日付やキーワードである程度絞ってから読む。
3. **リアルタイム購読（onSnapshot）は「今見ている画面に必要な範囲」だけに限定し、画面を離れたら確実に解除（unsubscribe）する。** 購読しっぱなしは読み取り回数を静かに消費し続けます。
4. **一覧のポーリングや自動リロードのような「読み続ける」実装をしない。** Firestoreのリアルタイム同期はプッシュ型なので不要。
5. 職員数が少ない（学生の卒制規模）前提のため、Authentication・Hostingの無料枠は事実上上限に達しません。

上記の範囲であれば、**維持費0円で運用できます。**

### 実装方針（Phase 2 の具体化）

- 認証: Firebase Authentication（メール/パスワード）
- データ: Cloud Firestore（施設 > 個体 > 記録／体重のサブコレクション構成）
- 写真: Cloud Storage（圧縮後アップロード）
- オフライン対応: Firestore のローカルキャッシュ永続化を有効化（Wi-Fiが弱い場所でも記録→復帰時に自動同期）
- ホスティング: Firebase Hosting（無料。GitHub Pages でも代替可）
- 削除: 論理削除（`deletedAt`）＋ゴミ箱画面（⑤）
- 学生本人が行う作業: Firebase プロジェクトの新規作成（無料・カード登録不要）と、発行された接続情報（APIキー等）をアプリ側の設定ファイルに貼り付ける作業。手順は `docs/SETUP-FIREBASE.md` にまとめます。
